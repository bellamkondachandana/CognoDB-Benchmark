# CognoDB Cloud Benchmark — WEXA AI Assignment 1

## Objective

This repository implements a reproducible, honest benchmark of **CognoDB Cloud** against four managed graph database platforms: **Neo4j, Memgraph, FalkorDB and ArangoDB**.

The assignment requires the same dataset, logical workloads, client machine and region as closely as possible, warm-up, p50/p95 reporting, automation, and explicit caveats. This harness does **not** fabricate benchmark numbers.

## Important limitation

Actual benchmark results require real database instances and credentials. The repository is ready to run, but the final results matrix must be generated by executing it against the five configured services. Do not replace missing measurements with estimates.

## Dataset

**SNAP Wiki-Vote**: 7,115 nodes and 103,689 directed relationships.

Source: https://snap.stanford.edu/data/wiki-Vote.html

Prepare it:

```bash
python prepare_dataset.py
```

The script downloads the public source and creates `data/edges.csv`.

## Database selection

| Platform | Why included |
|---|---|
| CognoDB Cloud | Target platform |
| Neo4j | Widely used property-graph/Cypher platform |
| Memgraph | Managed/hostable Cypher-compatible graph database |
| FalkorDB | Redis-compatible graph database |
| ArangoDB | Managed multi-model database with graph support |

Each provider must be run on the free/entry tier or a self-hosted deployment capped to equivalent resources. Record the actual vCPU, RAM and storage in `config.yaml` and below before submission.

## Environment and fairness

Use the same client machine and region for every platform. Record:

- client CPU/RAM/OS
- Python version
- region
- network setup
- provider tier
- vCPU/RAM/storage
- any burst/throttling limits

The assignment specifically warns against comparing unequal resources.

## Workloads

Every adapter implements the same logical workload categories:

1. Load: total wall-clock time, nodes/s, relationships/s.
2. 1-hop traversal.
3. 2-hop traversal.
4. 3-hop traversal.
5. Point lookup.
6. Indexed/filtered lookup.
7. Aggregation.
8. Mixed concurrent read/write at 1, 10 and 40 clients.
9. Observable footprint.

Read workloads use 100 measured iterations after 20 warm-up iterations by default. Latency is reported as p50 and p95.

### Indexed lookup note

The harness uses the `User.id` property for point/indexed lookup. Before the final run, verify that each provider has an actual index/primary-key optimization for this property and document it. If a provider cannot expose equivalent indexing, mark the metric/caveat rather than pretending it is equivalent.

```bash

```

Fill `.env` with real credentials. **Never commit `.env`.**

Then:

```bash
python prepare_dataset.py
python benchmark.py
```

Results are written to:

```text
results/raw_results.csv
```

## Analysis template

After the benchmark, discuss:

- Which system had the lowest p50 and p95 for each traversal depth?
- How did p95 change relative to p50?
- Which system loaded the graph fastest?
- How did concurrency affect mixed read/write throughput?
- Were any systems throttled or rate-limited?
- Were all resource tiers truly comparable?
- What query-language or feature differences could explain observed differences?
- Which results are not directly comparable, and why?

Avoid claiming a universal winner from one small benchmark.
